# Стройцены Бийск

Веб-приложение для сравнения цен на стройматериалы в магазинах Бийска. Цены собираются заранее
в базу данных (SQLite), поиск идёт по базе — быстро и без нагрузки на сайты магазинов при каждом запросе.

## Запуск

```powershell
# Установка зависимостей (один раз)
python -m pip install -r requirements.txt

# Собрать цены со всех подключённых магазинов
python -m app.run_scrape --all
# Или с одного магазина:
python -m app.run_scrape --store stroymir

# Запустить веб-приложение
python -m uvicorn app.main:app --port 8000
```

Открыть в браузере: http://127.0.0.1:8000

## Тесты

```powershell
python -m unittest discover -s tests -t .
```

Тестов 54, внешних зависимостей у них нет (stdlib `unittest`, отдельная временная база).
Покрыты разбор размеров/фасовки/цены/строк сметы и логика поиска и сметы целиком.

## Настройки (переменные окружения)

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `STROY_AUTO_SCRAPE` | `1` | `0` выключает фоновое обновление (удобно на время отладки) |
| `STROY_SCRAPE_INTERVAL_HOURS` | `12` | Период фонового обновления |
| `STROY_ADMIN_TOKEN` | не задан | Токен для `POST /api/refresh/{slug}`. Без него эндпоинт доступен только с localhost |
| `STROY_DB_PATH` | `prices.db` рядом с проектом | Путь к базе (используется тестами) |

Пока сервер запущен, встроенный планировщик (APScheduler) обновляет цены каждые
`STROY_SCRAPE_INTERVAL_HOURS` часов. Первый прогон — через этот же интервал после старта,
поэтому свежую базу нужно один раз собрать вручную (`run_scrape --all`).

**Про несколько воркеров:** планировщик живёт внутри процесса приложения, поэтому запускать
uvicorn с `--workers N` нельзя — обход стартанёт N раз одновременно. Для нескольких воркеров
выносите обновление в отдельный процесс (`run_scrape --all` по cron / планировщику задач)
и ставьте `STROY_AUTO_SCRAPE=0`.

## Как добавить новый магазин

1. Изучить структуру страницы категории: селекторы карточки товара, названия, цены.
2. Создать `app/scrapers/<slug>.py` с классом-наследником `BaseScraper` (см. `app/scrapers/base.py`)
   и методом `fetch_products() -> list[ProductRecord]`. Загрузку страниц делать только через
   `self._get()` — он сам проверяет `robots.txt` и держит паузу между запросами.
3. Зарегистрировать его в `app/scrapers/__init__.py` (словарь `SCRAPERS`).
4. Проверить: `python -m app.run_scrape --store <slug>`, свериться вручную с сайтом магазина.

## Как это устроено

- **Скрапинг.** `BaseScraper._get()` читает `robots.txt` магазина (`urllib.robotparser`),
  отказывается загружать запрещённые URL и выдерживает `Crawl-delay` (минимум 1 с).
  Прогон, вернувший 0 пригодных товаров, не считается успешным: база остаётся нетронутой.
  Товары, пропавшие из каталога, помечаются `is_active = 0` и исчезают из выдачи, но остаются
  в базе. Если прогон принёс меньше половины известных товаров, деактивация не выполняется —
  это похоже на сломавшуюся разметку, а не на распродажу.
- **Поиск.** Ключевые слова приводятся к нижнему регистру (SQLite умеет `LOWER()` только для
  ASCII, поэтому в базе лежит отдельное поле `search_text`, лоуеркейснутое в Python).
  Сначала ищем по всем словам запроса; если ничего нет — по первому слову (тип товара),
  ранжируя по числу совпавших слов. В ответе это помечено флагом `relaxed`.
- **Сравнение цен.** Из названия извлекается фасовка (`50кг`, `10 л`, `2,44×1,22 м` → м²)
  и считается цена за единицу. Бейдж «Лучшая цена» присваивается по цене за единицу и только
  внутри одной единицы измерения — иначе пакет смеси 2 кг за 154 ₽ выигрывает у мешка 50 кг
  за 580 ₽ (77 ₽/кг против 11,6 ₽/кг).
- **Смета.** Количество и размеры разбирает один и тот же код на бэкенде
  (`POST /api/parse-lines`), поэтому «Уголок 50 х 50» не превращается в 50 штук уголка.
  Закреплённые вручную товары считаются по актуальной цене из базы, а не по снимку в браузере.

## Ограничения текущей версии

- **Единицы продажи магазины не публикуют.** Фасовка вычисляется из названия и распознаётся
  примерно у трети каталога (4 353 из 14 154 товаров). Если фасовки нет, товар участвует в
  поиске, но бейдж «Лучшая цена» в такой выдаче не выставляется — сравнивать нечего.
- **Совпадение товаров — по словам названия, а не по артикулу.** Дословно одинаковых названий
  в двух магазинах всего два; пересечение по типу товара — около трети. То есть «где дешевле»
  отвечает на вопрос «где дешевле похожий товар», а не «этот же самый».
- **Количество в смете считается в упаковках.** Товар с фасовкой более чем в 5 раз крупнее
  типичной (биг-бэг 1 т вместо мешка 50 кг) в автоподбор не идёт, даже если он выгоднее
  за килограмм, но остаётся доступен через «Показать похожие / изменить».
- **У Алтерры `robots.txt` запрещает параметр пагинации**, поэтому по каждой подкатегории
  собирается только первая страница — охват каталога заведомо неполный.
- **Поиск идёт через `LIKE '%…%'`** — полное сканирование таблицы. На 14 тысячах товаров это
  15–40 мс, но при кратном росте каталога понадобится полнотекстовый индекс (SQLite FTS5).
- Истории цен нет: каждый прогон перезаписывает текущую цену.
